# CLAUDE.md — Old Money (рабочее название)

3D-игра про чужака, который строит тайную империю под полями английских лордов.
Полный дизайн-документ: «Old Money — дизайн-документ игры» (Claude Docs). Этот файл — правила для кода.

## Текущая фаза: 1 — прототип петли (недели 1–5)

Цель фазы — проверить, весело ли в основной петле БЕЗ сюжета.
Ворота фазы: 5 человек играют без подсказок и хотят продолжать.

### В объёме фазы
1. Сцена «Поле»: поле, грунтовая дорожка, контейнер на краю поля.
2. Контейнер: стеллаж отодвигается → лифт → подземная плантация.
3. Плантация: грядки с растениями, стадии роста, полив/уход, сбор урожая.
4. Время: ускоренные сутки, рост идёт по игровому времени.
5. Продажа: один NPC-покупатель, цена зависит от качества, деньги на HUD.
6. Найм: один работник, который сам ухаживает за грядками (видно, как он работает).
7. Сохранение и загрузка.

### Вне объёма фазы (не делать, даже если «быстро»)
Сюжет, диалоги с выбором, Схемщики, перемотка, полиция, драки, машины,
Лондон, озвучка, мультиплеер. Если задача тянет сюда — остановись и спроси.

## Камера и вид
- 3D low-poly, камера сверху под углом (изометрия, как в управленческих играх).
- Камера: панорама (WASD / края экрана), зум колесом, поворот на 90° (Q/E).
- Игрок управляет персонажем Джеком кликом мыши (навигация по NavigationRegion3D).
- Подземная плантация — отдельная сцена-уровень; переход через лифт в контейнере
  (затемнение экрана, смена сцены). Не делать «разрез» мира.
- Персонажи маленькие на экране: детализация моделей минимальная.

## Стек
- Godot 4 (последняя стабильная 4.x), GDScript со строгой типизацией.
- Тесты: GUT, запуск без графики:
  `godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://tests -gexit`
- Графика: low-poly модели по правилам STYLE.md (одна палитра-атлас на весь мир).
  Модели можно делать скриптами Blender (bpy) с экспортом в .glb; до этого — примитивы-заглушки.
- Перед любой визуальной работой прочитай STYLE.md. Цвета — только из assets/textures/palette.json.

## Архитектура (обязательно)
Симуляция решает — сцены только показывают.

```
res://
  sim/            # чистая логика, БЕЗ Node/сцен: классы extends RefCounted
    sim_state.gd      # всё состояние игры, сериализуемое
    sim_clock.gd      # игровое время
    economy.gd        # деньги, цены
    grow.gd           # рост растений
    workers.gd        # работники и их задачи
    event_log.gd      # журнал событий (всё важное пишется сюда)
    rng.gd            # детерминированный ГСЧ с зерном
  content/        # данные: .tres ресурсы (сорта, цены, работники)
  assets/
    textures/         # palette_atlas.png + palette.json (единственная текстура мира)
    models/           # .glb по категориям
  tools/blender/  # bpy-скрипты генерации моделей (запуск: blender -b -P <script>)
  scenes/         # 3D-сцены и UI, читают sim и шлют в неё команды
  autoload/
    game.gd           # единственная точка доступа к SimState
  tests/          # GUT-тесты для sim/
```

### Правила
- `sim/` не импортирует ничего из `scenes/` и не использует Node, сигналы сцен, `get_tree()`.
- Сцена меняет состояние ТОЛЬКО через команды: `Game.sim.apply(command)`.
- Каждое значимое изменение пишет событие в `event_log` (тип, время, участники, данные).
  Позже из журнала строятся улики, перемотка и мультиплеер — не обходить.
- Вся случайность — только через `sim/rng.gd` с зерном. Никаких `randi()` / `randf()` напрямую.
- Числа баланса (время роста, цены, зарплаты) — в `content/`, не в коде.
- Сохранение = сериализация `SimState` + `event_log` в JSON.

## Стиль кода
- Строгие типы везде: `var x: int`, `func f(a: float) -> void`.
- Никаких `Variant` там, где тип известен.
- Имена говорят сами за себя, без болтливых комментариев.
- Один класс — одна ответственность. Файл > 300 строк — повод разделить.
- Не добавлять плагины и аддоны без разрешения (кроме GUT).

## Как работать
1. Перед задачей: короткий план (что меняется, какие файлы, какие риски).
2. Логику в `sim/` писать вместе с тестами.
3. После изменения: прогнать тесты headless, исправить падения.
4. Не трогать то, о чём не просили. Изменения маленькие и проверяемые.
5. В конце: что сделано, что проверено, что осталось. Если была ошибка по ходу —
   «Ошибка: [что]. Правильно: [почему]».

## Чего Claude не видит
Claude не видит запущенную игру и не чувствует «весело ли».
Всё про ощущение, камеру, баланс и визуал проверяет человек.
Если задача требует посмотреть на игру — попроси скриншот или описание.
